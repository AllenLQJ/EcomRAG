# 灵码智能客服：演示准备

虚构店铺「灵码」，面向 C 端顾客的电商 RAG 智能客服。本文给出演示问题清单和演示前检查清单。标「已实测」的现象来自真实模型下的评测或接口调用；标「待实测」的尚未在真实环境验证，演示前请先走一遍。

## 一、演示主线（建议 8–10 分钟）

1. 开场：一句话介绍链路 —— 限流 → 缓存 → 常见问题 → 意图路由 → 检索 → 重排 → 带引用生成，资料不足就拒答。
2. 秒回：FAQ 命中。
3. 知识库回答：带引用，点引用跳到来源卡片。
4. 追问（多轮上下文）。
5. 拒答与敏感问题：不乱答、不泄露。
6. 打开「查看链路」，讲每个阶段耗时。
7. 流式输出与手机宽度（可选）。

### 5. 闲聊
你好、你可以做什么：自称「灵码客服助手」，引导回店铺问题。已实测。

### 6. 链路展示
页头点「查看链路」（演示部署需用 `VITE_SHOW_TRACE_TOGGLE=1` 构建），再问一个知识库问题，面板里按顺序是：缓存 → 常见问题 → 路由 → 检索 → 重排 → 生成 → 总计。讲解点：
- 路由约 3–5 秒（大模型分类并改写问句），重排约 2.5–3 秒（本机模型），生成约 2–6 秒。
- 口语短问法分数低时会出现第二次「重排（改写问题补充重排）」。
- 同一问题第二次问走缓存，阶段只剩「缓存」。

## 三、可以主动讲的数据（已实测）

- 24 题标准评测：路由准确率 100%，知识库引用命中 8/8，0 错误；总耗时中位数约 5.5 秒（glm-5.3-flash，机器空闲时）。
- 34 题口语评测集：路由准确率 100%，没有该答被拒、也没有该拒被答。
- 拒答阈值 0.2 + 生成器「资料不足输出 NO_ANSWER」双保险。
- 6 路并发流式提问：5 路成功，慢的约 30 秒（受跨境网络和本机重排串行限制）。

## 六、项目过程中遇到的问题与解决

按「现象 → 原因 → 解决 → 验证」记录。被评委问到「做的过程中有什么难点」时，可以从这里挑。验证结果均来自真实模型下的评测或接口调用。

### A. 稳定性与并发

**1. 两个人同时提问，第二个人直接看到「服务有点忙」**
- 现象：并发请求立刻返回 50302，连只查 FAQ 的请求也被拒。
- 原因：模型调用走一个单线程池，且在飞任务上限只有 1，名额用完就「非阻塞」拒绝，没有排队。另外，路由判为闲聊或敏感后，被丢弃的投机检索线程仍会占着名额跑完，下一个请求也被连带拒绝。
- 解决：改成有界排队。执行线程仍为 1（模型锁本就串行），新增 `MODEL_IO_QUEUE_SIZE`（默认 8，除正在执行的以外最多排队数）和排队超时（默认 20 秒）；执行加排队数达到上限才立即返回 50302；排队超时或请求被取消时不占名额、取消的排队任务不再执行；限流使用独立线程池，不与模型共用。
- 验证：并发排队的单元测试（含取消不泄漏名额、投机任务被丢弃后下一请求可排队）；5～6 路同时提问全部成功。

**2. 多人提问时被上游限流，提示「提问有点快，休息一分钟再问吧」**
- 现象：4 人同时提问，第 3、4 个请求立即失败，日志里是智谱返回 HTTP 429、错误码 1302「账户已达到速率限制」。
- 原因：账号对模型调用有并发上限，而客户端并发默认 4，429 只重试 1 次、退避 0.5 秒，前两个调用 4～8 秒内还没结束，重试必然再次 429。最终映射成本服务自己的限流码 42901，文案误导用户以为自己问得太快。
- 解决：客户端并发信号量默认降到 2，超出的在本地排队，不打到上游；429 单独重试 3 次，指数退避 1/2/4 秒，带 `Retry-After` 时取较大值且最多 8 秒；退避期间释放并发名额，重试时重新排队；仍失败时返回 50302（HTTP 503，「服务有点忙」），42901 只留给本服务自己的限流。
- 验证：并发测试通过；实测该账号至少允许 5 并发，建议 `LLM_MAX_CONCURRENCY=4`，6 路并发 5 路成功。

**3. 调用智谱偶发挂起 20 秒后超时，同一问题再问就好了**
- 现象：约三分之一请求出现 504 或 502；日志里是 `ConnectError`（约 4.5 秒后）或单次调用恰好超时。
- 原因：用户在海外，访问智谱国内服务器，新建连接和首包不稳定；旧代码对超时不重试，且网络重试合计只有 1 次。
- 解决：单次超时从 20 秒缩短为 12 秒；网络错误与超时统一重试 `LLM_NETWORK_RETRIES=3` 次，退避 0.5/1/2 秒并带少量抖动；httpx 显式配置连接池，复用已建立的 TLS 连接（`LLM_KEEPALIVE_S=60`）；重试前要求整请求预算至少还剩「退避时间 + 5 秒」（`LLM_MIN_ATTEMPT_S`），原来要求剩 12 秒，会让「排队加抖动后剩 9 秒」的请求白白放弃一次本可成功的重试。
- 验证：评测与压测中多次出现 `llm_retry` 后成功；24 题评测 0 错误。根治办法是改用智谱国际站（需确认账号），属于待办。

**4. 超时、取消后线程池被占满，一个请求超时会连带后面的请求**
- 原因：超时或客户端取消后，已经开始的检索、重排线程无法被强行中断，仍占着线程池和模型锁；限流也用同一个池。
- 解决：检索与重排用独立线程池并限制在飞数量，限流与它隔离；被取消的排队任务不再执行；关闭服务时有收尾超时，不会被挂死的线程卡住。
- 验证：Cursor 审核确认限流与模型池隔离、在飞计数无泄漏；对应单元测试。

### B. 回答质量

**5. 口语短问法被误判为「没有相关资料」**
- 现象：「发票怎么开」「保修多久」「支持哪些付款方式」等明明有文档，却被拒答。
- 原因：重排模型对口语短问法打分偏低，且与文档措辞（如「申请发票」）差异大。实测「发票怎么开」最高 0.14，而真正该拒答的「能保证我用耳机后听力会恢复吗」也是 0.14 左右，两者同一水平，**单靠调低阈值无法区分**。
- 解决（四层）：
  1. 路由让大模型把口语问题改写成与店铺文档措辞一致的完整书面问句（如「怎么改收货地址」→「如何申请修改订单的收货地址？」），实测分数从 0.37 提到 0.70；
  2. 原问低于阈值时，用改写后的问句再做一次补充重排，两次分数取高者（只补救低分，不增加高分问题的延迟）；
  3. 去掉了「改写与原问相似度 ≥0.8 就不补充重排」的门槛：「支持哪些付款方式」改写后只多了「店铺」两个字，相似度 0.89，被跳过，而改写后分数从 0.08 变成 0.69；
  4. 拒答阈值由 0.5 调到 0.2（口语集实测应答类最低约 0.20～0.44，应拒类最高 0.09），并增加生成器兜底：资料无法回答时只输出固定标记 `NO_ANSWER`，系统转成统一拒答文案。
- 验证：34 题口语评测集，路由准确率 100%，没有「该答被拒」也没有「该拒被答」。

**6. 前端候选问题点了答不出来**
- 原因：「运费怎么算」「发票怎么开」在 FAQ 里没有精确条目，走知识库检索，口语分数低。
- 解决：补充 FAQ 条目（答案严格取自现有文档，不编造），并补同义问法；这类高频问题直接秒回。

**7. 「你这里有什么商品」「你们卖什么」答不了**
- 原因：只有 4 份商品详情文档，没有总览，笼统问题与每份详情的相关度都只有 0.01 左右。
- 解决：新增 `product_catalog.md`（商品总览，内容全部摘自详情文档，不编造），并补 FAQ。
- 遗留：检索评测里商品总览在一题上抢到第一名，Hit@1 由 8/8 变成 7/8，回答不受影响，属于已知小问题。

**8. 回答引用了不相关的资料**
- 现象：一个划痕问题返回了 3 条来源，后两条相关度只有 0.02～0.04，模型还把它们引用成 [2][3]。
- 解决：生成前先过滤，只保留最高分和分数 ≥0.1 的资料（`RAG_CONTEXT_MIN_SCORE`），重新编号再交给生成；返回的 sources 只保留回答里实际引用的；回答完全无法依据资料时转为拒答。
- 验证：划痕问题现在只引用 1 条相关来源。

### C. 换模型与配置

**9. 换成 glm-5.3-flash 后全部请求报 400**
- 原因：该模型始终思考，不支持原来的 `thinking: disabled`（上游错误码 1210）；而且思考 token 计入 `max_tokens`，原来路由 64、生成 600 的上限会被思考吃满，返回内容为空、`finish_reason=length`。
- 解决：`LLM_EXTRA_BODY={"thinking":{"type":"enabled","effort":"low"}}`；路由 `max_tokens` 提到 2048，生成提到 4096（只是上限，不增加平时消耗）；`eval.llm_ping` 改用与线上相同的配置，并输出 `finish_reason` 和思考 token 数；错误诊断里针对 1210 和「思考吃满配额」给出明确提示。
- 验证：路由 2～6 秒、生成 2～7 秒；24 题总耗时中位数从约 8.5 秒降到约 5.5 秒。

**10. 配置覆盖导致行为不一致**
- 现象：代码默认值改了，但行为没变。
- 原因：`.env` 里的同名配置优先于代码默认值，且 `.env` 受权限限制，代码代理读写不了。
- 解决：把必须由使用者修改的项写进交接说明和本文检查清单：`LLM_EXTRA_BODY`、`REFUSE_THRESHOLD`、两个 `max_tokens`、`LLM_MAX_CONCURRENCY`、限流项。

### D. 功能与前端

**11. 回答要等 5～14 秒才一次性出现**
- 解决：新增流式接口 `POST /api/v1/chat/stream`（SSE，事件为 meta、status、delta、done、error，每 10 秒一个心跳）。前端先显示分阶段进度，再逐字渲染，结束后才渲染引用、来源卡片和标签；流开始前失败会自动退回整段返回接口，用户无感。
- 难点：`NO_ANSWER` 标记可能被拆在多个增量里，需要先缓冲、确认不是标记再放行；首个字之前可以重试，已经输出内容之后出错就不再重试，直接发 error 事件；客户端断开时要取消上游并释放并发与排队名额。
- 审核发现并修复：读屏逐字播报过度、`reader.cancel()` 后再 `releaseLock()` 抛错、新对话时旧流事件写进新会话（加入会话代次校验）、客户端断开时对话记录丢失、半截的 `NO_ANS` 前缀被当成回答发出。

**12. 多轮上下文**
- 问题：每个问题独立处理，「那台灯呢」这种追问检索不到。
- 解决：前端附带最近 3 轮历史；后端用历史把追问改写成完整问句，检索、重排、FAQ 都用改写后的问句；有历史时不读写缓存（防止同一句追问在不同上下文里串答）、投机检索关闭；历史作为不可信数据块，里面的指令不执行；对话记录只存历史条数，不存历史原文。
- 状态：单元测试通过，真实环境实测见第二章「追问」一节（待实测）。

**13. 前端视觉与交互问题**

**14. 公网访问时所有访客共用一个限流额度**
- 原因：经过隧道或反向代理后，后端看到的都是本机地址，每 IP 每分钟 10 次的限流变成全体共用。
- 解决：新增 `CLIENT_IP_HEADER`（部署时设为 `cf-connecting-ip`）和 `TRUSTED_PROXIES`（默认只信任本机 127.0.0.1/::1）；只有请求来自可信代理时才读取该请求头，防止外部伪造头绕过限流。
- 注意：后端必须只监听 127.0.0.1，不能直接暴露公网。

### E. 环境与工具链

**15. 机器内存耗尽，重排从 2.5 秒变成 22 秒，大量超时**
- 现象：所有请求变慢甚至 504，连 FAQ 都从 0.1 秒变成 2～4 秒。
- 原因：这台机器 16 GB，同时运行 Docker（Milvus、MySQL、Redis）、嵌入与重排模型、桌面应用和远程桌面，swap 几乎用满（13 GB），系统负载 74，模型运算都在和硬盘换内存。代码本身没有问题。
- 解决：重启电脑，只保留必要应用，关闭远程桌面和不用的大应用；演示前确认内存压力为绿色；可选的缓解是把重排改成半精度（fp16），实测更快且排序一致，内存约减半。

**16. 依赖服务没起来，后端启动失败**
- 现象：后端启动时报「服务暂时不可用」，数据库迁移报连接被拒绝。
- 原因：Docker 里的 Milvus、MySQL、Redis 在会话间停止了，容器和数据卷还在。
- 解决：`docker compose up -d` 并等三项 healthy；之后需先 `ingest.migrate_db` 再启动后端（对话记录表新增了历史条数字段，旧库需要补列，脚本是幂等的）。

**17. 前端依赖安装慢、中断后出现空目录**
- 现象：到 npm 官方源的单次请求要 16 秒，安装看起来卡死；中断安装后构建报找不到 `@rollup/rollup-darwin-arm64`。
- 原因：网络慢；中断时留下一个空的原生依赖目录。
- 解决：用镜像源只对这一次安装生效（不改全局配置）；删除空目录后重新安装；确认锁文件里没有镜像地址再提交。

**18. 协作与工具问题**
- 同一个代理的任务原本串行：把代理并发配置改为不同工作目录可并行，同一目录仍串行；已用两个只读审核任务验证。
- 新建编码任务被拒（已跟踪文件有未提交修改）：编码任务基于 HEAD，所以提交后再新建，或用续接任务沿用原工作树。
- 审核任务偶发失败（钥匙串写入失败、TLS 断开）：换请求编号重试，不动钥匙串与凭据。
- 同步工作树到主目录时误复制了不明来源的 `.env.save`：根因是 rsync 的 `--exclude .env*` 没加引号被 shell 展开；已删除该文件并修正脚本，之后同步一律用带引号的排除参数。
- 重复的请求编号会被幂等地返回旧任务（曾因此拿到已取消的旧任务）：每次新任务换新编号。
- 终端命令含中文、`×` 等非 ASCII 字符会被拒绝：含中文的命令写成脚本文件再运行。
